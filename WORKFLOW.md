# Голосовой ассистент с самообучением — Workflow

## 1. Концепция

На вход подаются **голосовые команды** для управления компьютером.
Набор команд расширяется — **вручную и автоматически**.

- Голосовой ввод обрабатывается на предмет команды.
- Команда есть в списке → **сразу исполняем**.
- Команды нет → обрабатываем через LLM (многоступенчато, см. раздел 2).

Система **самообучающаяся**: новая команда или скилл, созданная большой LLM,
сохраняется с тестами и кодовыми словами — при следующем вызове
она срабатывает мгновенно, без участия моделей.

### Определения

- **Команда** — элементарное действие (то, что уже есть в `commands.json`):
  измененить громкость, пауза, открыть приложение. Исполняется ядром.
- **Скилл** — составное действие: последовательность команд/шагов или скрипт
  с параметрами из речи. Примеры: «погода» (запрос к API → форматирование →
  озвучка), «поиск в интернете» (открыть браузер → ввести запрос → озвучить),
  поиск по гео-радиусу. Хранится под хост, выбирается скилл-LLM.

  Примеры скиллов с параметрами, которые скилл-LLM извлекает из речи:
  - «расскажи про погоду в **Ульяновске** на **завтра**» →
    skill `weather`, параметры `{city: "Ульяновск", when: "завтра"}`;
  - «поищи **бензин** в радиусе **3 км** от моего расположения» →
    skill `geo_search`, параметры `{query: "бензин", radius_km: 3}`.
- **Оркестратор** — детерминированная логика **самого ядра** (наш код на Python,
  покрыт тестами). Он решает, на каком уровне обрабатывать ввод и куда
  эскалировать. Оркестрация НЕ внутри большой LLM — та лишь исполнитель
  разработки (см. раздел 3).

## 2. Пайплайн обработки голосового ввода

```
Голос → STT (Vosk) → текст
          │
          ▼
   ЯДРО / ОРКЕСТРАТОР (CommandMatcher, commands.json, детерминированная логика)
          │
   ┌──────┴───────┐
   │ есть команда │  ──►  исполнение сразу
   └──────┬───────┘
          ▼  (команды нет)
      МИНИ-LLM (быстрая модель, малый контекст)
          │  исправить ошибку распознавания / найти готовую команду
   ┌──────┴────────────┐
   │ понятно → выполнить │
   └──────┬────────────┘
          ▼  (готовой команды нет / это сложное намерение)
      СКИЛЛ-LLM (понимает сложные намерения)
          │  подобрать скилл / собрать последовательность команд
   ┌──────┴────────────┐
   │ есть скилл → запуск │  (шаги, параметры из речи)
   └──────┬────────────┘
          ▼  (скилла нет / не хватает возможностей)
      БОЛЬШАЯ-LLM (разработчик)
          │  уточняет у пользователя ГОЛОСОМ, что он имел в виду
          │  TDD-цикл: тест → реализация → проверка
          │  создаёт/дорабатывает КОМАНДУ или СКИЛЛ
          │  (делегирует субзадачи мелким моделям через OpenCode CLI)
          ▼
   сохраняются под хост (commands.json + skills/ + tests/)
   → в следующий раз core / мини / скилл срабатывают без большой LLM
```

Параллельно всё время работает **модель-контролёр** — перехватывает
исходящие от большой LLM действия (выполнение, запись файлов, выбор моделей)
и проверяет их на надёжность (критерии защиты обсуждаются отдельно).

## 3. Роли моделей

| Модель | Приоритет | Задача | Характер |
|---|---|---|---|
| **Мини-LLM** | скорость | посмотреть список команд и подобрать подходящую под текущий ввод; распознать **ошибку распознавания** (например «сделай кромку пожалйста» = «сделай громче») | быстрые модели, малый/средний контекст |
| **Скилл-LLM** | понимание намерений | разобрать **сложные намерения**: подобрать готовый скилл или собрать последовательность готовых команд; вытащить параметры из речи (город, запрос, число…) | модель среднего веса, умеет «собирать сценарий», а не генерировать код |
| **Большая-LLM** | надёжность | написать рабочий код и тесты, убедиться что работает и ничего не сломает (TDD); вести диалог уточнения с пользователем; создавать/дорабатывать **команды и скиллы** | медленные думающие модели или **комбо** моделей; может делегировать части разработки мелким моделям (через OpenCode CLI) |
| **Модель-контролёр** | безопасность | перехватывать действия большой LLM (выполнение команд, запись файлов, доступ к моделям), проверять на неблагонадёжность | критерии защиты — обсудить отдельно |

### Оркестратор

Оркестратором является **ядро** (наш Python-код): оно детерминированно решает,
на каком уровне обрабатывать ввод (core → мини-LLM → скилл-LLM → большая-LLM),
управляет диалогом и эскалацией, следит за контекстом. Большая LLM НЕ
оркестрирует всю систему — она рабочий инструмент для разработки новых
команд/скиллов и может внутри (как «лид») делегировать субзадачи другим
моделям. Такая схема тестируема (TDD) и предсказуема.

## 4. Взаимодействие с OpenCode CLI

- Большая LLM вызывается **через CLI OpenCode** (`opencode` subprocess).
- При вызове указывается **модель или комбо моделей омнироутера**.
- Мини-LLM **ничего не решает сама** — она только сравнивает ввод со списком
  команд и определяет, ошибка ли это распознавания (с учётом контекста,
  например: идёт воспроизведение → «сделай кромку» = управление громкостью).
- Не смогла → передаёт большую LLM (через OpenCode CLI с указанием комбо).

## 5. Хранение команд и скиллов (принцип «под хост»)

- Скрипты, команды и скиллы пишутся **под хост**, на котором запускаются:
  `targets/<hostname>/commands.json` + скрипты в `targets/<hostname>/commands/`.
- **Скиллы** — отдельное хранилище под хост (предлагаемая структура,
  согласовать): `targets/<host>/skills/<skill>.json` (имя, шаблоны фраз,
  шаги/команды, параметры) + `targets/<host>/skills/<skill>.py` при сложной логике.

  Пример манифеста скилла (черновик):
  ```json
  {
      "skill": "weather",
      "phrases": ["погода", "расскажи про погоду"],
      "params": {"city": "текст", "when": "сегодня|завтра|потом"},
      "steps": [
          {"call": "llm.ask", "prompt": "погода в {city} на {when}"},
          {"call": "tts.speak", "text": "$result"}
      ]
  }
  ```
  Скилл-LLM на входе получает текст + список манифестов и возвращает
  выбранный скилл + заполненные параметры.
- На другом хосте — другие команды, другая обвязка, другой пользователь.
- Текущая структура commands.json сохраняется:
  `match` (шаблоны фраз) → `commands` (shell-строка/per-OS dict).

## 6. TDD-цикл создания новой команды

Пример: голосовая команда **«открой пожалуйста ютуб»**.

1. Ядро не находит команду в commands.json.
2. Мини-LLM не может сопоставить (нет такого намерения в списке).
3. Большая LLM уточняет у пользователя голосом, что именно нужно
   (открыть вкладку браузера с ютубом → нажать play и т.д.).
4. Большая LLM пишет **тест** — подтверждает желаемое поведение
   (открыта вкладка / осуществлён переход на вкладку с ютубом,
   нажата кнопка play).
5. Под тест пишется функционал (Make it pass).
6. Запускается проверка (pytest) — всё зелёное, ничего не сломано.
7. В commands.json добавляются `match`-шаблоны («открой ютуб», «включи ютуб», …)
   и ссылка на команду.
8. Следующий вызов этой команды — мгновенное исполнение ядром без LLM.

Аналогичный цикл для **скилла** (пример «погода в Ульяновске на завтра»):
тест на извлечение параметров `{city, when}` + на шаги манифеста
(запрос к API, форматирование ответа, озвучка) → реализация →
в `targets/<host>/skills/weather.json` → следующий раз скилл-LLM
срабатывает на готовом манифесте.

Работаем в **TDD**: тест → реализация → проверка → интеграция.

## 7. Модели омнироутера

- Сейчас: `auto` (модель подбирает сам OmniRouter).
- Позже: анализируем **статистику** использования и создаём **комбо** моделей
  для разных целей (быстрое сопоставление, генерация кода, диалог, контроль).

## 8. Принципы и ограничения

- **TDD** — новые команды/скрипты только с тестами.
- Покрытие целиком тестами должно оставаться (проект на 100%).
- Существующая логика сохраняется:
  - распознавание во время озвучки не останавливается (нужно для стоп-слова);
  - при озвучке реагируем только на стоп-слова;
  - прерывание синтеза и воспроизведения по стоп-слову;
  - suppress-окно после озвучки против эха.
- Большая LLM работает в **изолированной/безопасной среде** и её действия
  проходят через модель-контролёр.

## 9. Сравнение с существующими проектами (GitHub, исследование)

Цельной реализации нашей концепции на GitHub **нет** — никто не связывает
вместе «мини-LLM под ошибки распознавания + большая LLM через OpenCode CLI
под конкретный хост + автосоздание команд с тестами (TDD) + модель-контролёр».
Ближайшие аналоги покрывают только отдельные куски; ниже — что можно взять.

| Проект | Что даёт | Чем не подходит |
|---|---|---|
| [SLLMS](https://github.com/zactonz/sllms-framework) | offline-пайплайн STT→intent-парсинг LLM→инструменты→TTS; «fast-path команды + LLM как fallback» = наша схема; tool registry + allowlist | нет самообучения; 1 star, молодой; локальные whisper/llama |
| [RouteLLM](https://github.com/lm-sys/RouteLLM) (5.4k★) | готовые роутеры «быстрая ↔ сильная» (MF/bandit/BERT) + калибровка порога — база для нашего auto/комбо | только маршрутизация текста, без голоса |
| [kymaman/jarvis](https://github.com/kymaman/jarvis) | fast/deep-разделение моделей + wake word + STT/TTS + сэндбокс инструментов | роутер rule-based, нет самообучения |
| [PersonalJarvis](https://github.com/PersonalJarvis/PersonalJarvis) (38★) | «tool model» решает, сколько всего нужно; скиллы-плагины (brain/stt/tts/wakeword/harness); Ollama | нет автосоздания команд с TDD |
| [CowAgent](https://github.com/zhayujie/CowAgent) | создаёт и запускает скиллы, self-evolution | текстовый чат, не голос; без per-host логики |
| [agent-seed](https://github.com/jcurbelo/agent-seed) | «LLM предлагает новых агентов через PR + тесты, /learn» — паттерн саморазвития | контекст-файлы для кодинг-агентов, не голосовые команды |
| [Home Assistant / Rhasspy](https://community.home-assistant.io/t/conversation-automation-fallback-to-llm/835043) | паттерн «сначала локальный интент, fallback на LLM» | умный дом; нет создания команд |
| [nebulento (OpenVoiceOS)](https://github.com/OpenVoiceOS/nebulento) | rapidfuzz fuzzy-intent-парсер, толерантен к ошибкам/перестановкам — готовая основа мини-слоя | только парсинг, не LLM |
| [yuvakunaal/AI-Voice-Desktop-Assistant](https://github.com/Yuvakunaal/AI-Voice-Desktop-Assistant) | локальный fuzzy-поиск + LLM-intent для открытия приложений/сайтов | нет самообучения |
| [moonshine-ai](https://github.com/moonshine-ai/moonshine) (11k★) | низколатентное on-device STT/intent/TTS | «кирпич», не ассистент |

**Решение:** не переходим на чужой фреймворк — эволюционируем свой код.
Берём точечно: подход RouteLLM (роутер порога для mini/big), rapidfuzz/nebulento
(мини-матчер ошибок распознавания), fast-path паттерн SLLMS,
pattern «skills через PR/ревью» из agent-seed/CowAgent.
