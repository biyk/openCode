# Voice Control Project - Agent Guidelines

Голосовой ассистент на Windows: Vosk STT → обработка команд → TTS. Речь — это поток строк STT;
разбор команды идёт по правилу «ключ и команда в одной строке» (см. §10), затем — decision-слой Laya, intent, opencode.

## 1. Git commits — ТОЛЬКО ПО ЯВНОЙ КОМАНДЕ
- **Коммитить, пушить, делать PR запрещено без явной команды пользователя.** Сначала показать результат и ждать подтверждения.
- Исключение: авто-коммиты от хуков (`.git/hooks/post-commit` bump-версии) — их создаёт сам хук, агент не инициирует.
- Без команды не вызывать `git commit` / `git push` / `git add`, даже если задача выглядит завершённой.
- **Окончание разработки озвучивается вслух** («Разработка завершена»): текст — `lib/core/tuning.py::TASK_DONE_TEXT`, произносит его `.git/hooks/post-commit` через `python scripts/announce_done.py` (коммит и есть момент завершения; озвучка на bump-коммите не дублируется — хук выходит до неё). Поэтому «закончил разработку» без слова пользователя — это всё равно не коммит: сначала показать результат и ждать команду, а голос подтвердит факт коммита. Проверено тестами `tests/core/test_tuning.py::TestDevelopmentDoneIsAnnounced` (ловят тихую потерю озвучки).

## 2. Version gate
- `main.py` при старте и в потоке `lib/versioning/version_checker.py` (интервал 120 c) сверяет **app version** (`lib/__init__.py::__version__`) с **project version** (`VERSION`). При несовпадении — жёсткий выход (`os._exit(1)`).
- Если процесс «внезапно выходит» или тесты ломаются — первым делом проверять `lib/versioning/version_gate.py` + `version_checker.py`.
- После bump-коммита `VERSION` и `__version__` синхронны; не рассинхронизировать их вручную.

## 3. Build / Lint / Test Commands (Windows)

```bash
# Все тесты
python -m pytest tests/ -v

# Один файл / один тест
python -m pytest tests/core/test_orchestrator.py -v
python -m pytest tests/core/test_orchestrator.py::TestOrchestratorProcess::test_process_text_command_found -v

# Линейные новые тесты тоже в подпапках-зеркалах: tests/voice_cmd/, tests/runtime/, ...

# Линт — ТОЛЬКО этой командой (совпадает с pre-commit):
flake8 --max-line-length=100 --exclude=venv,temp,.git,.pytest_cache,__pycache__ lib/ tests/ scripts/ main.py reauth.py

# Запуск приложения
python main.py
```

- **Всегда `python -m pytest`**: голый `pytest.exe` (Scripts\pytest.exe) не кладёт корень репо в `sys.path`, и `lib.*` не импортируется (Windows).
- Файла `.flake8`/`setup.cfg` нет: лимит 100 и эксклюды задаются исключительно флагом CLI (как выше).
- mypy: конфиг `mypy.ini`, запуск **неблокирующий** — `python scripts/check_types.py` (строгие зоны `lib/voice_cmd`, `lib/core`); в pre-commit не входит, пока зоны не чисты (тогда флаг `--fail`).
- Живые тесты (`tests/browser/test_youtube_live.py`, `tests/google/test_calendar_live.py`, `tests/taskflow/test_task_live.py`, live-громкость) требуют окружения — браузер CDP на `:9222`, OAuth-токены — и флейкят. Pre-commit гоняет **весь** набор, так что без рабочего окружения коммит может упасть на живом тесте.

## 4. Архитектура (wiring)
- Цепочка: `main.py` → `lib/stt/transcription_worker.py` (цикл: Vosk → `_fix_encoding` → обработка) → `Orchestrator.process_text` в `lib/core/orchestrator.py`.
- `Orchestrator` — набор миксинов в `lib/core/`: `orchestrator.py` (детерминированное ядро), `orchestrator_decision.py` (уровень Laya), `orchestrator_memory.py` (laya/undefined-кандидаты базы знаний), `orchestrator_llm.py` (LLM-детект id команды + параметр), `orchestrator_llm_bg.py` (фоновая очередь этого детекта), `orchestrator_opencode.py` (фолбэк), `orchestrator_speech.py` (стоп-слова, dev-режим).
- Уровни обработки текста (по порядку):
  1. `commands.json` — детерминированный матч (ключ и команда в одной строке, §10);
  2. decision-слой Laya — распознанные Laya команды, `lib/core/laya_decision.py`, §4.2;
     2.1. внутри промаха Laya: EventMatch (нераспознанное мероприятие) → LLM-детект команды **в фоне** (§4.9);
  3. legacy mini-intent — `lib/voice_cmd/intent.py` (фабрика `build_intent`);
  4. фолбэк — console opencode (`lib/opencode/opencode_cli.py`).
- Конфиг команд устройства — `targets/<hostname>/commands.json` (путь определяет `lib/voice_cmd/config_loader.py::get_device_commands_path`). В `requires` команды перечислены статусы (`proxy`, `browser_youtube`, …) — **статусы-требованиЯ блокируют команду** (частая причина «не работает включи ютуб»). VPN-статус заменён на `proxy` в `lib/runtime/status_checkers.py`.

### 4.2 Decision-слой Laya
- Конфиг секции `decision` в `targets/<host>/commands.json`: `enabled`, `url` (http://127.0.0.1:8080), `threshold` (~0.5), `auto_launch` (`laya-lab/bin/laya.exe` + gguf-модель).
- `LayaDecision.detect(text)` → `(choice, confidence)` либо `None` (порог из конфига, критерии — id команд). Фабрика `build_decision(matcher, output)` сама читает конфиг; `build_intent` — аналог в `lib/voice_cmd/intent.py`.
- Воркер создаёт их в `lib/stt/transcription_worker.py`. Путь обработки с дефектной речью проверен тестами `tests/core/test_decision_chain.py` («открой я туб» → openyoutube).

### 4.3 Фоновый контроль таблицы задач (`task_monitor`)
- `main.py` рядом с CronScheduler поднимает `lib/core/task_monitor.py` (daemon-поток, как version_checker): раз в `interval_min` читает `real_life_tasks` через `lib/taskflow/task_check.py`.
- Ни одной запущенной задачи (`start_date = 0` у всех строк) → вслух «чем ты сейчас занимаешься?», следующая строка STT — ответ: название ищется среди задач таблицы (`TaskStartHandler.find_task_event`) и найденное запускается (`start_task`, то же, что `taskstart`).
- **Пока идёт мероприятие «СОН» молчит ВЕСЬ цикл** (решение пользователя; ночью не должно быть ни уведомлений, ни сообщений). Вердикт держит `lib/core/sleep_gate.py` — единственный источник правды: `check_sleeping()` читает сегодняшние события календаря (`sleep_now`: начало ≤ now < конца), обновляет кэш и строку «Сон» в панели «Сервисы»; `is_sleeping()` — дешёвое чтение без сети, его подставляют в гейты. `tick()` спрашивает сон ПЕРВЫМ делом (ДО `overtime.check`) и возвращает `"sleep"`: нет озвучки, вопроса, Telegram-оффера/notify, проверки активного окна (`RestWatch`) и оповещения о переработке. Кэш обновляют: фоновый опрос статусов (checker `sleep`, статус `sleeping` в `targets/<host>/status.json`, интервал 60 с — поэтому запись в status.json обязательна, иначе опрос вердикт не трогает) и каждый цикл монитора (`sleep_fn=check_sleeping` в `task_monitor_launch`). **При запуске приложения сон НЕ проверяем** (решение пользователя): вердикт считает только цикл уже запущенного приложения — первые доли минуты после старта гейт молчит (`is_sleeping()` = False), и это принято сознательно, никакого `warm()`-чтения в `main.py` быть не должно.
- **Сбой календаря (как и пустой ответ) вердикт НЕ меняет — липкость** (решение пользователя, раньше был fail-open). Прежний `_today_events()` отдавал `None` → «не спим» → обрыв сети/токена посреди ночи снимал молчание, и монитор сыпал вопросами и кнопками в Telegram (ловилось живьём в `logs/`: `Идёт «СОН» — вопрос снят` в 23:38, а в 23:49 и 00:00 — снова `[Ask] Вопрос (task_idle)`). На свежем процессе вердикта нет — там по-прежнему «не спим»: молчание не должно включаться из-за сломанного календаря. Завершившийся или будущий (вечерний) «СОН» вопроса не снимают. Тесты: `tests/core/test_sleep_gate.py` (липкость, кэш, панель), `tests/core/test_sleep_wiring.py` (порядок в `tick`, `reply` не под гейтом, статус в конфиге), `tests/core/test_task_monitor_sleep.py`, ветки `sleep_now` — `tests/taskflow/test_task_schedule.py`.
- **Переработка** (тот же цикл, шаг до вопроса): запущенная задача идёт дольше `task_time × overtime_multiplier` (колонка B real_life_tasks, дефолт 1.2) → Оповещение «Всё ли в порядке?» **озвучивается, выводится в консоль/лог и дублируется в Telegram**. Это НЕ вопрос с ожиданием ответа (`ask`) — только сообщение (`say`), отвечать не ждём. **ПОКА задача в переработке оповещение ПОВТОРЯЕТСЯ на каждый такт монитора** (интервал `task_monitor.interval_min`, по умолчанию 10 мин) — signal это `say`, а не открытый `pending`-вопрос, поэтому строки STT не съедает и не висит. Раньше стояла «разовость» (одно на запущенную задачу) — баг: длинная задача замолкала после первого сигнала; убрана. `OvertimeNotifier.remind_min` (`REMIND_MIN_DEFAULT`, 0) — минимальная пауза между повторами, `_last_ms` чистится по `running` (рестарт → новый сигнал). Реализация — `lib/core/overtime.py::OvertimeNotifier` (чистая детекция — `task_check.find_overtime`), дубль в чат — `TelegramBot.broadcast`. Снятие этого оповещения «по решению пользователя» — ЛОЖЬ (было убрано только ожидание ответа, а не сама переработка). Во время «СОН» оповещение СНЯТО НАСТОЯЩЕЕ (решение пользователя): `tick()` проверяет сон ДО `overtime.check` — держит тест `tests/core/test_task_monitor_sleep.py::TestSleepSilencesOvertime` (раньше гейт стоял только в idle-ветке, и переработка будила спящего каждую десятиминутку).
- **Классификатор активного окна («отдых ли это») ходит на маршруте `auto/tools`** (решение пользователя; раньше — дефолт клиента `auto/best-fast`). Константа `REST_MODEL` в `lib/rest_check.py`, переопределяется ключом `rest_model` секции `task_monitor` в `targets/<host>/commands.json` (он же прокидывает фабрика `task_monitor_launch` через `partial(classify_until_answer, model=...)`). Это **не имя модели**, а комбо OmniRouter: роутер сам выбирает шаг (`comboStepId` в его call_logs). Замер по 110 запросам: `auto/best-fast` садился на `mistral/codestral-latest` в 85% ответов (qwen3.8-flash 13%, qwen3.8-27b 3%), и `auto/tools` на этом ПК выбрал тот же codestral — значит физическую модель меняет только правка комбо в самом OmniRouter или явный id модели в `rest_model`. **Фолбэк — на ТОТ ЖЕ маршрут:** клиент создаётся один на все попытки цикла `classify_until_answer` (сбой шага комбо не уводит запрос на другую модель); пауза 5 с, без потолка попыток, поэтому проверка ушла в отдельный поток `RestWatch` и не задерживает вопрос монитора. 31 из 110 запросов были сбоями (504/499/429/403/400) — поэтому ретраи, а не разовая проба. Тесты: `tests/test_rest_check.py::TestRestModel` (маршрут по умолчанию, переопределение, «один клиент на все ретраи»), `tests/core/test_task_monitor_rest.py::TestRouteFromConfig` (фабрика прокидывает `rest_model`); живая проверка — `python temp/rest_model_live.py` (вердикт + кто реально ответил по call_logs), история маршрутов — `python temp/omni_rest_models.py`.
- Вопрос/ответ — `lib/core/orchestrator_ask.py`: строка после вопроса перехватывается ДО уровней §10 и живёт `answer_timeout_s` секунд; просроченный вопрос снимается и переспрашивается в следующий цикл (иначе один неотвеченный заблокировал бы все), «стоп» снимает вопрос. **Снятие вопроса зовёт `on_expire`** — им monitor передаёт `recall` Telegram: реплика вопроса с кнопками, оставшаяся в чате после просрочки, провоцирует ответ там, где ответа уже не ждут (иначе «вопрос задан → пользователь ответил голосом/кнопкой → время вышло» выглядит как недопонимание). `ask(question, on_answer, label, timeout_s, on_expire)` — сигнатура, её держит и заглушка в тестах. Секция `task_monitor` в `targets/<host>/commands.json` (enabled/interval_min/answer_timeout_s/overtime_enabled/overtime_multiplier/rest_model, дефолты — `lib/core/tuning.py` и `REST_MODEL`). Тесты: `tests/core/test_task_monitor.py`, `tests/core/test_task_monitor_overtime.py`, `tests/core/test_overtime.py`, `tests/core/test_orchestrator_ask.py`, `tests/core/test_task_monitor_notify.py` (в т.ч. `TestIdleQuestionRecall`: `on_expire` = переданный `recall`, при `recall=None` ничего не снимается), `tests/taskflow/test_task_check.py` (переработка закреплена тестами — не удалять).

### 4.4 Развлечения в дырах календаря (`fun_holes`)
- Тот же поток `task_monitor`, отдельный шаг каждый цикл (независимо от idle/busy и от того, читалась ли таблица): `lib/taskflow/fun_fill.py`.
- **Дыра** — промежуток между двумя соседними событиями `colorId=7` (цвет «сделано» задач приложения), даже если между ними стоят события других цветов. Окно: от конца сегодняшнего «СОН» (пробуждение) до начала последней синей задачи — то есть только прошедшее время, куда автоплан уже не пишет. Промежуток короче `min_gap_min` не заполняется; пересекающиеся галочки сворачиваются бегущим максимумом конца (дыра не может быть отрицательной).
- В дыру вставляется событие `FUN_EVENT_TITLE` («Отдых») на весь промежуток, `colorId` — у сегодняшнего мероприятия «тест для цвета» (пользователь задаёт цвет им; ищется за `lookback_days`, иначе `FUN_FALLBACK_COLOR`). Имя награды `FUN_REWARD_TITLE` («1час развлечений» из `real_life_rewards`) остаётся только в журнале списаний — в календаре оно было бы шумом.
- **Деньги**: `hero_money -= минуты события` (1 минута = 1 hero_money, минус разрешён), и в `rewards_history` идёт строка теми же колонками, что JS-клиент: `uuid | claim_ms | gold_spent | reward_title | reward_id | серий_даты` (`lib/taskflow/rewards_sheet.py`).
- Идемпотентность: развлечение НЕ синее, поэтому соседи по цвету после вставки те же — без маркера одна и та же дыра тратилась бы каждый цикл. Маркер `fun_hole` в `description` события; дыра, внутри которой есть такое событие, пропускается. Озвучки нет (решение пользователя) — виден факт в календаре и в таблице, а **каждое действие пишется в `logs/fun_holes.log`** (JSONL: `action=fill` — дыра, `gold_spent`, `event_id`, `claim_item_id`; `action=run` — итог прохода). Ручная проверка: `python -m lib.taskflow.fun_fill [--dry]`. Тесты: `tests/taskflow/test_fun_holes.py`, `test_fun_fill.py`, `test_rewards_sheet.py`.

### 4.5 Браузер: ждать события страницы, а не время
- Причина: «открой юту» матчится, браузер поднимается, а в ответ — `[Browser] Не удалось запустить текущее видео`. Виноваты паузы: код жал play() по ещё не загрузившейся вкладке и считал это успехом.
- Порядок шагов один для всех сценариев: **порт браузера → событие загрузки → элемент в DOM → факт воспроизведения**. `browser_control.ensure_browser` ждёт ответ `/json/version` (опрос `CDP_POLL_S`, потолок `BROWSER_START_S` — события тут нет), дальше `lib/browser/cdp_events.py`.
- `cdp_events.wait_page_loaded` / `navigate` — подписка `Page.enable` и `Page.loadEventFired` (у навигации ещё ответ `Page.navigate`; `errorText`/`error` = переход не удался). Документ мог загрузиться до подписки — признаком служит `readyState`.
- `cdp_events.wait_condition` / `wait_element` — JS-Promise внутри страницы: `MutationObserver` + редкий `setInterval` (состояние плеера `video.paused` в DOM не отражено). Возврат `false` по истечении `timeout` — это «не дождались», а не ошибка.
- Две ловушки, пойманные только живым браузером: (а) выражение должно быть ОДНИМ `new Promise(...) {...}` без завершающих `()` — иначе `TypeError: (intermediate value) is not a function`; (б) ответ вида `{"error":{ "code":-32000, "Cannot find default execution context"}}` — это не провал условия, а перезапуск документа: запрос повторяем до дедлайна.
- Таймауты в `lib/core/tuning.py` — только страховки от зависшей вкладки (`CDP_PAGE_LOAD_S`, `CDP_ELEMENT_S`, `BROWSER_START_S`); `CDP_FIRST_TRY_S` — короткая первая проба: сразу после клика/перехода страница ещё документ-заглушка, поэтому `_wait_player_ready` пробует сначала быстро, потом по-настоящему.
- Проигрывание проверяется по состоянию страницы (`!document.querySelector('video').paused`), а не по тому, что вернул внедрённый скрипт. `wait_for_selector` из `cdp_client` удалён — его заменил `cdp_events.wait_element`.

### 4.6 Шлюз захвата микрофона (`record_gate`)
- Правило: **звук идёт НЕ через разрешённое устройство (наушники) и на нём играет медиа → микрофон не пишется**. С колонок медиа попадает в микрофон, и ассистент распознаёт чужую речь вместо команд; в наушниках утечки нет, там запись всегда открыта.
- `lib/runtime/record_gate.py::RecordGate` — daemon-поток (тот же порядок, что `task_monitor`), раз в `poll_s` читает Core Audio: `default_device_name()` + `active_session_processes(min_peak)` (`lib/runtime/audio_devices.py`, ctypes-COM через `lib/runtime/win_com.py`). Колбэк sounddevice только читает готовый `blocked` — COM в аудио-поток реального времени не пускаем.
- «Играет» решает **пик-метр сессии** (`IAudioMeterInformation::GetPeakValue`), а не `AudioState` — ловушка, найденная живой замером: спящий VLC висит `Active` с пиком 0.0 (по одному состоянию шлюз глушил микрофон непрерывно), а SoundPlayer играет при `state=1` с пиком 0.6. Порог — `RECORD_GATE_MIN_PEAK` (`record_gate.min_peak`); из состояний отсекаем только `Muted` (в микрофон такой не утекает). Метр не ответил — не считаем медиа (fail-open).
- Глушим **полностью** (решение пользователя): вместе с командами не слышны и стоп-слова. Выход из заглушения — пауза медиа или возврат на наушники; на каждом переключении worker сбрасывает распознаватель (`take_change()`), иначе склеился бы обрывок команды с музыкой.
- Своя озвучка — **тоже медиа** (решение пользователя, раньше было наоборот): TTS играет из дочерних `powershell`/`mpg123`/`ffplay`, и на колонках ассистент слушал сам себя — обрывки своих фраз становились командами и ответами на вопросы («ему велосипеды запущена»). Поэтому `lib/synth/tts_playback.py` пушем докладывает о начале/конце воспроизведения (`set_voice_listener` → `RecordGate.voice`), а `ignored_processes` по умолчанию пуст (скидка остаётся ручкой; по ней же глушатся и CLI-озвучки из чужих процессов, где пуш недоступен).
- Хвост `RECORD_GATE_VOICE_TAIL_S` (`record_gate.voice_tail_s`, 0.5 с) держит шлюз закрытым сразу после конца игры: между блоками одной фразы плеер перезапускается на миллисекунды, и без хвоста шлюз щёлкал бы на каждом блоке (а эхо последней фразы успело бы распознаться).
- Любой сбой проверки (COM, не Windows, неизвестное устройство) — **открытый** шлюз (fail-open): оглохнуть из-за сломанного условия хуже, чем из-за музыки.
- Секция `record_gate` в `targets/<host>/commands.json` (enabled/allowed_device/poll_s/min_peak/voice_tail_s/ignored_processes), дефолты — `lib/core/tuning.py` (`RECORD_GATE_*`; allowed_device — подстрока имени, регистр не важен). Шлюз собирает `build_record_gate(matcher, output, voice=tts)` в `__init__` worker'а (там же подписывает TTS), запускает `run()`, снимает `stop()`.
- Тесты: `tests/runtime/test_audio_devices.py` (что считается звуком: тишина при Active, пик при state=1, мьют, мёртвый метр), `tests/runtime/test_record_gate.py` (таблица случаев правила, fail-open, озвучка как медиа, фабрика), `tests/runtime/test_record_gate_voice.py` (пуш без лага опроса, наушники не глушим, хвост, отсутствие фликера, подписка в фабрике), `tests/synth/test_tts_voice.py` (переходы 0↔1, сбой слушателя не валит озвучку), `tests/stt/test_worker_record_gate.py` (колбэк и цикл захвата); живые проверки — `python temp/gate_peak.py` (пики всех сессий + вердикт из реального конфига) и `python temp/gate_peak2.py` (поднимает `temp/play_loop.ps1` и показывает, что шлюз закрывается ровно в моменты звука).

### 4.7 Команды из Telegram (`telegram`)
- Третий источник текста после микрофона и консоли: `lib/telegram/launch.py::start_telegram(worker, output)` поднимает daemon-поток long polling'а (`lib/telegram/bot.py::TelegramBot`) рядом с `task_monitor` (вызывается из `main.py`, там же `stop()`).
- Сообщение чата идёт **тем же путём, что печать в консоль**: `submit_manual_text(worker, text, reply=sink)` → `Orchestrator.process_text(text, reply=...)`, поэтому правило «ключ и команда в одной строке» (§10) и дописывание триггера не дублируются.
- `reply` — канал ответа запроса (миксин `lib/core/orchestrator_chat.py`): `_say`/`_report_blocked`/итог opencode уходят в чат, динамики молчат. Голосовой запрос (без reply) снимает канал. Строка чата — не эхо колонок, поэтому окно `_suppress_until` и гейт `_speaking` к ней не применяются; сериализация источников — замком `_input_lock` в `process_text`.
- Безопасность: бот запускает shell-команды на ПК, поэтому обязателен whitelist `allowed_chat_ids` (или `TELEGRAM_CHAT_IDS` в `.env`) — без него и без токена бот не стартует. Токен **только** из окружения по имени `token_env` (`.env`, в JSON его быть не может — файл в git). Сообщение из неизвестного чата логируется один раз со своим id — его и копировать в whitelist. Управление dev-режимом из чата отвергается (§6).
- Транспорт — `requests` (`lib/telegram/api.py`) плюс PySocks (он нужен для схемы `socks5h://`, добавлен в `requirements.txt`); `get_updates` возвращает `None` при сбой API (отдельно от пустого списка) → цикл делает паузу `retry_s`. Ответы режутся по `max_len` (4096) — чистая функция `lib/telegram/message.py::split_chunks` (пустые строки выбрасывает, строку длиннее лимита дробит). Тайминги — `TELEGRAM_*` в `lib/core/tuning.py`, секция `telegram` в `targets/<host>/commands.json` (enabled/token_env/allowed_chat_ids/proxy/poll_timeout_s/retry_s/max_len).
- **Прокси обязателен на этом ПК**: прямого маршрута до `api.telegram.org:443` нет (TCP-таймаут), есть SOCKS5 `192.168.1.107:1080` — тот же адрес, что у статуса `proxy` (`lib/runtime/status_checkers.py`). Ключ `proxy` (`socks5h://host:port` — DNS тоже через прокси) или `TELEGRAM_PROXY` в `.env`; PySocks уже в окружении. В лог прокси пишется без логина/пароля (`launch.py::proxy_label`), токен вырезается из текста ошибок requests.
- **Просроченный вопрос снимается из чата** (`deleteMessage`): `TaskOffers.offer` запоминает `message_id` каждого отправленного вопроса (по чатам), `TaskOffers.recall()` удаляет их и **забывает независимо от ответа Telegram** (отказ — не повод повторять на каждый такт); `send_message` вместо `True` возвращает именно `message_id` (None — не отправлено), поэтому память о вопросе собирается по ходу отправки. Канал один: `main.py` передаёт в `start_task_monitor` и `offer` (кнопки), и `recall`; монитор зовёт `recall` как `on_expire` вопроса (§4.3). Без кнопок (задач нет/календарь не прочитан) вопрос уходит в тот же `offer` пустым списком — `TaskOffers` сам шлёт текст, второго пути в чат в мониторе нет. Нажатие кнопки и `broadcast` (оповещение о переработке) память вопроса не трогают: снимать нечего, пока живой вопрос.
- **Инициатива снимается на время «СОН»** (решение пользователя: ночью боту не о чём писать самому): `TelegramBot(..., mute=is_sleeping)` ставит гейт на `broadcast` (оповещение о переработке) и `offer` (вопрос с кнопками) — чистая функция `lib/telegram/message.py::muted`, в лог строка `[Telegram] «СОН» — уведомление снято` (снятое видно, оно не «потерялось»). `reply` под гейтом НЕ стоит намеренно: иначе ночная команда в чате пропала бы без ответа. Сбой читалки вердикта = «не снято» (fail-open: гейт не цены доставке).
- Тесты: `tests/telegram/test_api.py`, `test_config.py`, `test_bot.py`, `test_bot_factory.py` (мок requests/Api), `tests/telegram/test_bot_mute.py` (broadcast/offer сняты, reply проходит, сбой гейта не глушит канал), `tests/telegram/test_message.py::TestMuted` (таблица случаев чистой функции), `tests/telegram/test_offers_recall.py` (память id, снятие по всем чатам, однократность, «не отправлено — не помним», новый вопрос вытесняет старые id), `tests/telegram/test_bot_callback.py::TestRecallProxy` (бот делегирует и реальный раунд-трип offer→recall), `tests/core/test_orchestrator_chat.py` (роутинг ответа), `tests/stt/test_text_inputs.py` (проброс reply).

### 4.8 Статистика использования команд (`command_stats`)
- Зачем: видно, какие команды реально запускаются, какие редко/никогда — чтобы удалять мёртвый функционал.
- Единственная точка учёта — `CommandMatcher.execute_by_id` (`lib/voice_cmd/commands.py`): через неё проходят все исполняемые пути (commands.json, база знаний, Laya, legacy intent). Считается **успешный** запуск (`ok=True`); неудача/блокировка по requires не прибавляет. Составная команда засчитывается по id sequence (шаги не дублируются).
- Хранение — `lib/voice_cmd/command_stats.py::CommandStats`, JSON рядом с commands.json устройства: `targets/<host>/command_stats.json` вида `{"cmd_id": {"count", "first_seen", "last_seen"}}`. Путь задаёт `stats_path_for(commands_file)`. Файл **в .gitignore** (runtime-данные, не должны шуметь в коммитах).
- Потокобезопасно (замок) и **fail-open**: сбой чтения/записи логируется `swallowed()` и НЕ валит выполнение команды — статистика не ценой команды.
- Отчёт: `python -m lib.voice_cmd.command_stats [--commands PATH]` сводит известные id (`commands` + `sequences`) со счётчиком, по возрастанию использования (никогда не служившие — сверху), подтягивает `descriptions`. stdout переключается в UTF-8 (описания с юникодом иначе падают на cp1251).
- Тесты: `tests/voice_cmd/test_command_stats.py` (счётчик, first/last_seen, corrupt/write-fail fail-open, сортировка отчёта, хук `execute_by_id`: успех пишет, неудача — нет, sequence пишет по составному id).

### 4.9 Фоновый LLM-детект команды (`orchestrator_llm_bg`)
- Баг 2026-10-02: «алиса оставь задача сделать короб под ванной» — промах по commands.json/Laya/EventMatch уводил в **синхронный** LLM-детект, а гонка (omni + lmstudio на localhost:1234 при выключенном сервере — ретраи) отвечала ~55 с. Всё это время `process_text` держал `_input_lock`, и цикл распознавания глох: следующие фразы не доходили ни до одного уровня (а после успеха стартовал **второй** такой же детект — вторая минута молчания).
- Решение: детект уходит в собственную очередь с daemon-воркером — точь-в-точь как console opencode (`orchestrator_opencode.py`). `orchestrator_decision.py` при промахе вызывает `self._enqueue_llm_fallback(text)` и **сразу return**, `_llm_pending()` поднимает тот же флаг, что `_opencode_active`.
- Классификация в воркере идёт ВНЕ лока, применение (`_apply_llm_command`) — в локе, с подменой `self._reply` на канал заявителя: фоновый ответ уходит в чат того, кто заказал, а не того, чей запрос активен в момент готовности (`orchestrator_chat`).
- Отмена — по **поколению** `_llm_gen`: стоп-слово (`maybe_abort`) и `stop()` зовут `_cancel_llm_fallback()` — чистит очередь и поднимает номер, а сидящий в `classify` воркер перед исполнением проверяет `cancelled=lambda: gen != self._llm_gen` и не исполняет снятую фразу (поэтому `_run_llm_fallback` принимает `reply`/`cancelled`; прямой синхронный вызов остался возможен — им пользуются тесты).
- Фоновый промах (`_llm_fallback_miss`) — тоже в воркере: undefined-корзина и «не распознано» в чат, но в локе и с восстановлением `_reply`.
- Тесты: `tests/core/test_orchestrator_llm.py::TestLlmFallbackIsBackground` (process_text возвращается за <1 с при зависшей гонке; «стоп» не даёт исполнить; новая команда в это время проходит уровни), `tests/core/test_orchestrator_opencode.py` — образец неблокирующего воркера.

### 4.10 Засечки длительности (`timing`)
- Зачем: между `[Command] Распознана команда: taskdone` и первым итогом висело ~15 c тишины. Виноваты не TTS и не Python: команду исполняет дочерний процесс, который делает ~12 ПОСЛЕДОВАТЕЛЬНЫХ запросов к Google (Calendar + Sheets) и молчит до самого конца. Замер только чтения (`python temp/probe_taskdone_timing.py`): импорты 0.33 с, `discovery.build("calendar")` до 2.5 с на холодную, `resolve_uuid` 2.4 с, чтения листа 1.6+0.9+1.1+0.3 с, `list_events` 1.1+0.6 с — 11.1 с, остальное добирают записи.

Сорвавшийся запрос помечен «сбой <Тип>» и летит наверх как раньше.

### 4.11 Микрофон: вход ноутбука; BT-микрофон гарнитуры — только по явной просьбе (`mic_stream`)
- Причина №1 (глухота): `_pick_mic_device` выбирал вход ровно ОДИН раз в начале `run()`, а Windows не переводит уже открытый PortAudio-поток на другое устройство. Поток висел на входе гарнитуры (`device=12`), микрофон ноутбука не открывался никогда — снятые наушники делали ассистента глухим.
- Причина №2 (цена первого «исправления»): **все входы BT-гарнитуры живут в профиле Hands-Free, а он не сосуществует со стерео-медиа.** Как только такой вход открыт, гарнитура уходит в режим разговора и её звук молчит — при этом Windows продолжает считать «Наушники (soundcore H30i)» активным устройством по умолчанию: ни состояние эндпоинтов (`IMMDevice::GetState`), ни дефолтный render ничего не показывают, **слышит только пользователь**. Попытка «микрофон следует за наушниками» открывала её вход при подключённых наушниках → пользователь терял весь звук в гарнитуре. Хуже того: переключение профиля само меняло дефолтный render, `headset_active()` отвечал False, мы закрывали BT-вход, A2DP возвращался — и цикл повторялся (в логе `[Mic]` прыгал каждые 10–40 с). **Правило: выбор микрофона не должен зависеть от состояния, на которое сам же и влияет.**
- Правило сейчас: пишем с микрофона ноутбука (`mic.laptop_device`, подстрока имени; не совпало — первый безопасный вход, потом системный). Звонковые входы отсекает `mic_devices.safe_inputs` по маркерам `CALL_INPUT_MARKERS` («hands-free», «bthhfenum», «головной телефон» — имя обрезано до 31 символа: «Головной телефон (soundcore H30», поэтому маркер, а не модель) и по токену гарнитуры. `headset_active()` при `headset_mic: false` не дёргается вовсе. Говорить в гарнитуру можно только явно: `mic.headset_mic: true` (цена — молчащая медиа-озвучка в наушниках). **Fail-open**: если безопасного входа нет вообще (единственный микрофон — гарнитура), берём его, иначе ассистент глохнет полностью. USB-гарнитуру не режем — конфликта профилей у неё нет.
- **Соединённость решает устройство воспроизведения, а не список входов**: проверено живьём — вход гарнитуры остаётся в перечислении PortAudio при выключенных наушниках (так же висят входы BH-07 и WAE-004), флага `available` в sounddevice 0.4.7 нет вовсе. Дефолтный render (`audio_devices.default_device_name`) при разрыве переключается на колонки сразу — `headset_active()` возвращает True/False/**None** (None = сбой COM/не Windows → решение не меняем). Системный вход тоже не доверенность: подключённая гарнитура становится дефолтным input, поэтому `_system_default` смотрит индекс среди безопасных.
- Реализация: `lib/runtime/mic_devices.py` (перечисление/матчинг/`safe_inputs`/`headset_active`/`default_input_index`) + `lib/stt/mic_stream.py` (`MicWatcher`, `build_mic_watcher`). `worker.run()` больше не использует `with sd.RawInputStream`: `self._mic.open(callback, sr, blocksize)` один раз, далее на каждой итерации `if self._mic.follow(): recognizer.Reset()` — смена входа закрывает старый поток и открывает новый (Reset нужен, чтобы хвост фразы с одного микрофона не склеился с началом речи на другом). В `finally` — `self._mic.close()`.
- Поток запускается ЯВНО (`stream.start()`): конструктор `RawInputStream` не играет — раньше это делал `with`, без `start()` захват молчал бы совсем.
- Опрос живёт в потоке цикла захвата (не в аудио-колбэке: COM в real-time колбэк пускать нельзя) и ограничен `mic.poll_s` (дефолт 2 с); неудачное открытие паркуется на `MIC_RETRY_S`, чтобы не долбить недоступное устройство каждым тактом. Дефолты секции `mic` — в `mic_stream.py` (`MIC_*`), а не в `tuning.py` (тот на пределе 200 строк, как и `flavor.py` §4).
- Секция `mic` в `targets/<host>/commands.json`: `headphone_device` (по умолчанию = `record_gate.allowed_device`), `laptop_device`, `headset_mic` (default false), `poll_s`; читается `matcher.get_mic_config()`. Смена входа печатается `[Mic] Микрофон: <имя>` — по этой строке видно, что происходит живьём (прыгающая без внешних причин строка = обратная связь правила и железа).
- Ручная проверка: `python -m lib.stt.mic_stream` (список входов + «Звук идёт в гарнитуру: …» + вердикт «Нужен этот вход»); держать процесс заглушённым помогает и `python temp/audio_state.py` (дефолтный render + активные сессии, ничего не открывает).
- Тесты: `tests/runtime/test_mic_devices.py` (в т.ч. `TestSafeInputs`: все живые формы имени BT-входа отсекаются, USB/ноутбучный остаются, fail-open на единственном звонковом), `tests/stt/test_mic_stream.py` (главный — `test_connected_headphones_keep_the_laptop_mic` и `test_probe_answer_does_not_move_the_target`: пока `headset_mic` выключен, соединённость не влияет на выбор, а значит петля обратной связи невозможна), `tests/stt/test_worker_mic_switch.py` (сквозной регресс: `run()` с настоящим `MicWatcher` НЕ берёт BT-вход при подключённых наушниках; исчезнувший вход пересобирает поток и сбрасывает распознаватель), `tests/stt/test_worker_record_gate.py` и `test_stt_command_integration.py` (мок `worker._mic`, `follow()=False`, патчи `sd` теперь на `lib.stt.mic_stream.sd`).

### 4.12 Скорость играющего видео (`playback_rate` — «алиса быстрее / медленней»)
- Третий канал управления звуком после громкости: `python -m lib.browser.playback_rate up|down [шаг]` → сдвигает `playbackRate` ролика, который **прямо сейчас звучит** с тестового браузера (:9222).
- **CDP не знает, какая вкладка звучит**: в `/json/list` нет поля `audible` (проверено живьём — только id/title/url/type/webSocketDebuggerUrl). Поэтому каждая обычная вкладка (`page_tabs` отсекает service worker и фоновые страницы расширений) спрашивается JS-пробой: среди `video`/`audio` ищется играющий (`!paused && !ended && readyState >= 2`), а звучащий — `!muted && volume > 0`.
- `sounding_tabs` сортирует найденные **звучащие вперёд, заглушённые — в хвост**, порядок внутри группы остаётся браузерным → повторная команда крутит ту же вкладку, а не прыгает по роликам. Вкладку НЕ активируем (`_activate` не зовём): `playbackRate` работает и с фоновой, а угон фокуса у пользователя ни за что.
- **Состояние читается с самого элемента каждый раз**, поэтому сброс скорости YouTube на новом ролике, ручная смена скорости в меню плеера и «1× после паузы» обрабатываются сами — своего состояния модуль не держит.
- Шаг = числовой параметр команды `step` (0.05) в `targets/<host>/commands.json` — тот же механизм, что `{{step}}` у громкости, и тюнится пер-девайсно. Границы `RATE_MIN`/`RATE_MAX` (0.25/4.0) — константы модуля: `tuning.py` на пределе 200 строк (§8), прецедент — `youtube_live.py::PLAYER_TIMEOUT_S`.
- **`requires` нет** (намеренно): статус `media` читает SMTC Windows и не видит, что играет именно вкладка, — он глушил бы команду ложно. Нечего крутить → код возврата 1 + озвучка «Ни одно видео не играет»: сдвиг на 0,05 почти не слышен, поэтому подтверждение направления («Быстрее»/«Медленней») важнее нейтрального «Готово», а молчье выглядело бы как непонятая команда. Озвучивает себя сам процесс-ребёнок (`_speak`, ленивый `TextToSpeech`) — образец `lib.shopping`/`lib.task_complete`; в `ACK_TEXTS` (§6) `rateup`/`ratedown` НЕ заносятся — иначе направление прозвучит дважды.
- **Ограничение**: плееры внутри iframe (встроенные ролики) пробой не видны — смотрим только основной документ.
- Тесты: `tests/browser/test_playback_rate.py` (выбор звучащей вкладки, clamp, «замолчала между пробой и сдвигом», отчёт), `tests/browser/test_playback_rate_cli.py` (арги, коды возврата, озвучка, провязка в commands.json: «быстрее»→rateup, «медленней/медленнее»→ratedown, «громче»/«тише» по-прежнему про громкость).

### 4.13 Монитор сервисов (вкладка «Сервисы» на доске знаний)
- Зачем: фоновых потоков и detached-процессов много (слушалка, шлюз записи, статусы, крон, TG, монитор задач, проверка версий, смотритель OmniRouter + Laya/браузер/доска), а видно их только по косвенным строкам лога. Панель показывает 🟢 работает, 🟡 ждёт своего такта/очереди, 🔴 выключен / ошибка / никогда не запускался.
- Потоки НЕ выносились в процессы и брокер не поднимали (решение пользователя — «сделай как проще и быстрее»; RabbitMQ отвергнут сознательно): цикл захвата — real-time PortAudio-колбэк, `record_gate` делает latency-критичные COM-вызовы, озвучка обязана начинаться мгновенно. Ради GUI платили бы скоростью основного цикла.
- Транспорт между процессами — heartbeat-файл: `lib/monitor/registry.py` (потокобезопасный словарь состояний; `report()` не бросает — реестр не цена сервиса) → `heartbeat.py` (`HeartbeatWriter` раз в `MONITOR_HEARTBEAT_S` атомарно, tmp + `os.replace`, пишет `temp/services_heartbeat.json` со штампом времени) → его читает `status.collect`.
- **Панель живёт ВНЕ основного процесса именно поэтому**: зависший или умерший main не может честно показать, что он завис. Просрочка heartbeat на `MONITOR_STALE_S` (8 с ≈ ×4 интервала сброса) → `status.collect` красит ВСЕ сервисы main в ERROR («основной процесс не отвечает»); файла нет вовсе → одна строка `main` в NEVER.
- **Отдельного сервера дашборда (порт 8766) больше нет — это была вторая сущность с теми же данными.** Вкладка «Сервисы» прицепляется к серверу доски знаний (:8765): `ui.install(board_html)` вставляет `<script>` перед `</body>` (файл `knowledge_review_ui.py` ровно на лимите 200 строк, поэтому инъекцией, как попап в `knowledge_review_ui_log.page()`), а данные отдаёт новый маршрут `GET /api/monitor` в `knowledge_review_server.py`. Скрипт ставит кнопку `data-t="services"` и `<section id="t-services">` — переключение вкладок делает штатный обработчик клика доски; опрос `/api/monitor` раз в 2 с, только когда вкладка видна (фоновый опрос не должен мешать досмотру знаний), прямая ссылка — `http://127.0.0.1:8765/#services`.
- Внешние процессы (Laya :8080, браузер CDP :9222, доска :8765, OmniRouter :20128) heartbeat не трогают — сервер доски сам пробабит их порты (`probes.py`): ответ 2xx = работает, молчанка = ждёт команды (жёлтый, а не красный: они поднимаются по требованию). `status._merge` склеивает id: пока heartbeat свежий, строка остаётся как её доложил сам процесс (смотритель знает, что он чинил); при просрочке берётся факт с порта — врать за чужой процесс зависший main не вправе. Дублирующих строк в панели не бывает.
- **Смотритель OmniRouter (`watchdog.py`) не только показывает, но и чинит** — LLM-прокси держит на себе ответы Laya-фолбэка, rest-классификацию и оживление ответа, а сам чужой процесс. Таблица решений: порт закрыт → `не запущен` → рестарт сразу; порт открыт, `/api/health` молчит → после `MONITOR_OMNI_HANG_FAILS` (3) подряд считаем «завис» → рестарт; health отвечает → зелёный, счётчик обнуляется. Рестарт не чаще `MONITOR_OMNI_COOLDOWN_S` (180 с): старт OmniRouter медленный (~10–20 с только CLI), иначе крутили бы рестарт на каждом такте, пока сервер греется. Поверх этого — `MONITOR_OMNI_WARMUP_S` (120 с) пауза на прогрев сразу после нашего рестарта: замерено живьём, что `serve --daemon` занимает порт за 0–6 с, а `/api/health` отвечает только с ~45-й секунды (подъём Next.js), и три такта по 15 с иначе ловили ещё не готовый сервер — смотритель убивал его как висячий и прокси не доживал до готовности. В прогреве вердикт `warmup` (жёлтый «греется после перезапуска»), счётчик неудач обнуляется; мёртвый порт прогрев НЕ прикрывает. Таймаут пробы здоровья отдельный (`MONITOR_OMNI_HEALTH_TIMEOUT_S` = 3 с): об общий `MONITOR_PROBE_TIMEOUT_S` (1 с) `/api/health` под нагрузкой спотыкается. Любой сбой проверки — fail-open (`swallowed`), смотритель не роняет ни себя, ни main.
- Чужие процессы сами не убиваем: `omni.restart` зовёт **собственный CLI** — `omniroute stop` (по pid-файлам `~/.omniroute/{server,supervisor}/.pid`, на win32 fallback kill по порту) и `omniroute serve --daemon --port N` (spawn detached). `omniroute restart --daemon` — так делать нельзя: у команды `restart` нет опции `--daemon` (Commander падает с «unknown option», rc=1 — именно так прокси и не поднимался), а без неё `restart` вызывает `runServe` в foreground того же процесса, и CLI никогда не вернулся бы; осечка `stop` не мешает старту (процесс мог упасть сам), а ok=True требует именно открытого порта. Слепой `kill node.exe` запрещён — в `node.exe` на этом ПК живёт редактор. Автозапуск OmniRouter на этом ПК — Resurrector (`C:\Users\b5\.config\resurrector\config.toml`, запись `[omniroute]` там `enabled = false`, то есть сейчас его supervisor выключен — наш смотритель работает вместо него).
- Проводка: `registry.report(...)` стоит во всех вечных циклах (`stt`, `record_gate`, `status_poll`, `cron`, `task_monitor`, `telegram`, `version_checker`) и в обоих фоновых воркерах (`orchestrator_opencode`, `orchestrator_llm_bg`). У `record_gate` и `task_monitor` цикл переписан с `while not self._stop.wait(x)` на `is_set()` + break — иначе нечем показать жёлтый ДО паузы. Выключенные опциональные сервисы (нет секции/выключены) помечаются DISABLED в `main.py` и воркере, поэтому красный в GUI — это решение конфига, а не «поток умер». Строку `omniroute` пишет только watchdog (из потока main), поэтому она честно краснеет вместе с main при зависании.
- Подключение: `start_monitor(worker._matcher, output)` в `main.py` рядом с остальными демонами, `monitor.stop()` — первым в shutdown; возвращает бандл `Monitor` (heartbeat + watchdog). Секция `monitor` (enabled/board_port/auto_open/omni_enabled/omni_url/omni_interval_s/omni_hang_fails/omni_cooldown_s/omni_warmup_s) читается `matcher.get_monitor_config()`; дефолты `MONITOR_*` — в `lib/monitor/tuning.py`, а не в `lib/core/tuning.py` (тот ровно на лимите 200 строк; прецедент — `MIC_*` в `mic_stream.py`, §4.11).
- GUI — вкладка дебаг-браузера (`browser_control.open_url`, §4.5), а не Tkinter; внутри JS-литерала нет backslash-продолжений и шаблонных литералов (известная яма этой кодовой базы). У `HeartbeatWriter`/`OmniWatchdog` флаг остановки называется `_stop_event`, а не `_stop`: у `threading.Thread` есть свой метод `_stop()`, и одноимённый атрибут ломает `join()` (`TypeError: 'Event' object is not callable`).
- Ручная проверка: `python -m lib.voice_cmd.knowledge_review launch --tab services` (поднимет доску и откроет именно `#services`; без `--tab` браузер показывает вкладку, которую помнит); сам `temp/services_heartbeat.json` — runtime-данные, в .gitignore (как `command_stats.json`, §4.8). Строка `omniroute` в этом файле — доказательство, что watchdog крутится (probe в heartbeat не пишет); живые замеры — `python temp/live_snapshot.py` (строки снапшота с :8765), `python temp/tab_live.py` (что реально отрисовано во вкладке на :9222), `python temp/watchdog_live.py` (найдённый CLI omniroute + вердикт на мёртвом порту; рестартер подменён заглушкой, живой прокси не трогается) и `python temp/omni_state.py` (heartbeat-строка omniroute + жив ли pid из `~/.omniroute/server/.pid` + обе пробы).
- Тесты: `tests/monitor/` (реестр в т.ч. 8×200 потоков, heartbeat-атомарность и fail-open и `join()`, слияние статуса и дедуп строк, пробы с замоканным `http_ok`, таблица решений watchdog + его цикл, `omni.py` с замоканными socket/CLI, фабрика `start_monitor` с поднятой доской) + `test_wiring.py` — гард по тексту исходников: каждый сервис обязан звать `registry.report("<id>")`, watchdog — докладывать `omniroute`, сервер доски — отдавать `/api/monitor` и `install()`, дашборда-файла быть не должно, heartbeat — в .gitignore; ловит тихое исчезновение сервиса из GUI. HTTP-часть — `tests/voice_cmd/test_knowledge_review_monitor.py`, якорь вкладки — `test_knowledge_review_launch.py`. Имена `test_monitor_status.py` (а не `test_status.py`) и `test_omni_process.py` (а не `test_omni.py`): в `tests/` нет пакетов, pytest грузит модули по basename, и одноимённые модули из разных папок (tests/runtime/test_status.py, tests/providers/test_omni.py) ломают коллективание всего `tests/`. ## 6. Аудио и стоп-слова
- `TranscriptionWorker` продолжает писать микрофон и во время TTS (распознавание стоп-слов живо) **только в наушниках**: с колонок шлюз §4.6 заглушает запись целиком, и свою фразу прервать голосом нельзя — «стоп» будет услышан уже после озвучки.
- Аборт: `abort_event` поддерживается в TTS и плеере.
- `_fix_encoding` не должен перекодировать уже валидный UTF-8 из Vosk.
- Частые причины «ассистент не остановился» — стоп-слова и кодировка (см. `_fix_encoding` в `lib/stt/transcription_worker.py`).
- `_fix_encoding` вынесен в `lib/stt/encoding.py` (worker ≤ лимита строк §9); имя `transcription_worker._fix_encoding` сохранено как алиас — тесты мокют его именно там.
- Ещё одна причина «ассистент молчит в ответ» — шлюз записи §4.6: с колонок играет медиа, и микрофон заглушён намеренно.
- **Кэш mp3 gTTS** (`lib/synth/tts_cache.py`): каждая озвученная фраза раньше пересоздавалась через сеть. Теперь gTTS пишет в `temp/mp3/<sha1(lang|text)>.mp3`, а `speak()` сначала ищет там: попадание — играет копию без сети (и работает офлайн), промах — синтез + `store`. `cached_copy` обновляет дату файла (он переживёт `purge`), `purge` удаляет древнее `TTL_DAYS=7` (срабатывает раз в час при записи). Кэш на диске — общий для долгоживущего воркера и коротких CLI-процессов. Проигрывание всегда идёт из временной копии, поэтому `_play_file` (удаляющий файл) не трогает кэш. Тесты: `tests/synth/test_tts_cache.py`.
- **Блочная озвучка** (`lib/synth/tts_pipeline.py::speak_blocks`): цель — не генерить то, что уже есть. Анонс режется на блоки (`_split_sentences` по пунктуации — запятая/точка = пауза), и каждый блок ищется в кэше отдельно. Конвейер кидает все блоки в пул сразу: кэшированные возвращаются мгновенно и играют, а новый (неизвестный) блок синтезируется **параллельно с проговариванием готового** — задержка сети прячется за озвучкой. Стабильные (ежедневные) фразы надо давать ОТДЕЛЬНЫМИ блоками от переменных данных: так фрейм кэшируется один раз на все задачи, а генерится только название. Пример — `lib/task_complete.py::_celebrate` возвращает СПИСОК блоков (`Задача выполнена.` / `<название>.` / `Вы умничка!` / `Следующая задача:` / `<след.>.`), а не одну строку. Тесты: `tests/synth/test_tts_pipeline.py::TestSpeakBlocks`.
- **Озвучка принятого действия** (`lib/core/orchestrator_speech.py::ACK_TEXTS` + `_ack(cmd_id)`): исполнитель shell-команды пишет лишь в консоль, поэтому голос без этой таблицы молчал («алиса начал уход за ногтями» → EventMatch → `python -m lib.task_start` → тишина). `_ack` зовётся на успех сразу после `_chat_done` во всех ветках (§10 level 1, `_execute_decision`, legacy intent, `_execute_event_action`). taskdone в таблице НЕТ — `lib/task_complete.py` хвалит сам, иначе одна мысль произносится дважды. Чату озвучка не дублируется (`_ack` выходит, есть канал reply). Тесты: `tests/core/test_task_start_ack.py` — новый уровень без озвучки или двойная реплика роняют их.

## 9. Версии и git-хуки
- `VERSION` — семантическая версия (major.minor.patch); `lib/__init__.py::__version__` держит ту же. Синхронизация — `scripts/bump_version.py patch|minor|major`.
- `.git/hooks/pre-commit` (при коммите выполняются ВСЕ проверки, порядок важен; упал — коммит не создан):
  1. `python -m pytest tests/ -q`;
  2. `python scripts/generate_commands_md.py --check` — актуальность COMMANDS.md;
  3. `flake8 --max-line-length=100 --exclude=...` (та же команда, что в §3);
  4. `python scripts/check_blind_except.py --git` — новые `except Exception` обязаны логировать (print/лог/raise/`swallowed()`/`# blind-ok`), сравнение с HEAD;
  5. `python scripts/check_lengths.py --git` — **лимит 200 строк** у каждого файла (py/ps1/bat);
  6. `python scripts/check_tooltips.py --git` — **каждый новый файл обязан иметь описание в `.structure.json`**;
  7. `python scripts/generate_structure.py --check` — STRUCTURE.md должен быть регенерирован.
- Если хук упал: для (4) — заменить глухой `except` на `swallowed(...)` (или `# blind-ok`); для (5) — урезать/разбить файл; для (6)+(7) — добавить строку в `.structure.json` и выполнить `python scripts/generate_structure.py --write`, затем пере-`git add`.
- `.git/hooks/post-commit` сам делает bump (patch) и коммит «Bump version to …» через `--no-verify` (чтобы не было цикла); bump-коммиты агент вручную не создаёт. После bump хук озвучивает завершение разработки (`scripts/announce_done.py`, §1) — ошибку озвучки глотает, на коммит не влияет.

## 10. Концепция голосовых команд (commands.json) — ЕДИНСТВЕННО ВЕРНАЯ

Первый уровень обработки — `commands.json`. Речь — поток строк STT; команда ищется **внутри одной строки** (триггер и команда в одной строке).

Обозначения:
- `[ключ]` — ключевое слово: триггер из `triggers` (`алиса`, `пожалуйста`).
- `_команда_` — слово/словосочетание, указывающее на действие (шаблоны из `match`).
- `{настройка}` — слово/словосочетание, определяющее параметр команды (после команды).

Правила поиска команды:
1. Ключ и команда должны стоять **в одной строке** — соседние строки (над/после) не смотрим и следующую строку не ждём.
2. Внутри строки ключ может стоять **где угодно** — до или после команды.
3. Команда — слово/словосочетание **сразу перед ключом или сразу после ключа** (в той же строке).
4. Команда определяется по **максимальному совпадению ≥ 90%** с match-шаблоном. **Не угадывать**: пользователь должен правильно произносить команды; ниже порога — мимо (ложный вызов).
5. Слова, идущие **дальше после команды** — настройки для неё.
6. Если в строке ключа команд нет (даже когда там одни триггеры) — **ложный вызов, игнорируем**: к decision-слою Laya (§4.2) уходит та же строка (STT коверкает фразы — «открой я туб» вместо «открой ютуб», и Laya такие варианты ловит).

Настройки (текущий набор):
- громче/тише: `{немного}` — уменьшить шаг в 2 раза; `{сильно}` — увеличить шаг в 2 раза (база 6% → 12%).
- быстрее/медленней: шаг скорости фиксированный — `step` = 0,05 (§4.12), словами не меняется.

Трассировка этапов печатается в консоль: `[Command] …` (match по commands.json) → `[Decision] Лайя: команда распознана «…» (c=…)` / `команда не распознана (запрос в OmniRouter заглушён, пропускаем)`.
