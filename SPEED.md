# SPEED.md — скоростные замеры и журнал оптимизаций

Цель: перед каждой оптимизацией снимать метрику «до», после — «после»,
сравнивать по истории в `tests/speed/results.json`. Обычный прогон
`pytest tests/` замеры НЕ запускает.

## Запуск

```powershell
$env:VOICE_SPEED="1"; python -m pytest tests/speed -v -s      # все замеры (~1 мин)
$env:VOICE_SPEED="1"; $env:VOICE_SPEED_LIVE="1"; python -m pytest tests/speed -v -s  # + живые LLM-провайдеры
python -m pytest tests/speed -k ensure -v -s                  # одна группа метрик
```

Каждый прогон дописывает медиану в `results.json` и печатает дельту к
прежнему значению: `[bench] metric: Xs [min..max] xN (prev Ys, +Z%)`.

## Журнал изменений

| Дата | Изменение | До | После |
|---|---|---|---|
| 2026-09-26 | baseline, замеров ещё не было | — | см. таблицы выше |
| 2026-09-26 | **Негативный TTL (5 с) в `ensure()`**: свежий результат фонового опроса не перепроверяется синхронно (`lib/runtime/status.py`, `status_poll.py`) | status.ensure_fresh_off = **5.9777 s** | **~0 s** (медиана; пик 2.2 s — частично протухшие замеры) |

Примечание к TTL: путь `ensure_all_off`/`missing_requires_worst` с
протухшими отметками специально остаётся медленным — это осознанная
перепроверка «вслепую». В запущенном приложении фоновый цикл держит
`_last_check` свежими, поэтому реальная блокировка команды теперь
мгновенная. Штатный риск: статус включили внешне — до 5 с команда
может продолжать блокироваться (следующий реплай речи уже успешен).
